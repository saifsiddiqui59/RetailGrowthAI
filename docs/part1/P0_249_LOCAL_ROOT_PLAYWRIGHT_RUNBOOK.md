## No TinyFish: operator-owned Windows/VS Code browser

The repository now has the *optional*, zero-cloud-change script `scripts/ops/p0249_root_canary_playwright.py`. It uses Chromium Playwright with an actual Platform Super Admin's email/password, signs in at the existing DEV website, and drives **only** the normal `Platform Control → Retailer signup approvals` UI. Decisions go through the existing audited ROOT RPC; no privileged database/grant override and no service-role key in the browser. The password is prompted without terminal echo, never supplied as a command argument, committed, printed, sent to GitHub, or saved to `storageState`/screenshots.

1. Open the repository's current `main` in VS Code Git Bash **on a machine with Internet/DNS access**. From the repository root:
   ```bash
   uv run --with playwright python -m playwright install chromium
   uv run --with playwright python scripts/ops/p0249_root_canary_playwright.py --approve-test-only --dispatch-dev-canary
   ```
2. Enter the **DEV ROOT email** and password at the local terminal prompt. Do **not** place a password in these commands. The script authenticates using the normal sign-in screen and must actually reach the `Retailer signup approvals` UI; a non-ROOT account fails closed.
3. Keep the visible browser and command open. After `ARMED: ROOT authenticated`, the helper snapshots existing pending requests and excludes them. With `--dispatch-dev-canary`, the helper uses the operator's existing authenticated `gh` GitHub CLI to intentionally dispatch the [protected DEV canary](https://github.com/saifsiddiqui59/RetailGrowthAI/actions/workflows/retail-dev-test-accounts-canary-once.yml) on `main` using `node-poster-reel` and the existing explicit DEV approval code. **Nothing is dispatched before ROOT UI readiness.** If GitHub CLI is unavailable, omit `--dispatch-dev-canary`, wait for `ARMED`, and manually run the same protected workflow from GitHub Actions.
4. The script polls **Refresh queue** and authorizes only a *new* exact-pattern `rgai-canary-<12 lowercase hex>-a@example.invalid` account, followed by the same-prefix `-b@example.invalid`. Each goes through **Review account → audited reason → explicit checkbox → Approve**, and requires an actual UI confirmation. Accounts already pending before ARMED, other users, other formats/domains and other canary prefixes are denied. It exits after two approved synthetic accounts or a bounded timeout. It cannot authorize after the test-run cleanup.
