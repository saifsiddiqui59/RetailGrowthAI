# P0 #249 — Microsoft official Azure Functions root-cause triage (28 October 2026)

**Research verdict:** high-priority suspected *Flex host specialization / Python worker gRPC readiness / request routing* fault, potentially worsened by the one-instance default single-request Python HTTP concurrency. **No causal per-request platform trace exists in the accessible evidence, so the precise cause is NOT PROVEN.** This review does **not** deploy code or Azure configuration, change spend, close issue #249, or authorize customer HTTP cutover.

## Official Microsoft documentation, with why each matters

1. [Azure Flex Consumption plan, Considerations](https://learn.microsoft.com/en-us/azure/azure-functions/flex-consumption-plan#considerations): **host initialization/specialization 30s non-configurable**; failed startup may log gRPC `System.TimeoutException`. This is distinct from the worker process startup limit. [Microsoft's official Functions host work item #10482](https://github.com/Azure/azure-functions-host/issues/10482) identifies 30s `WebHostRpcWorkerChannelManager.SpecializeAsync()` / `GrpcWorkerChannel.PendingItem.OnTimeout()`. Do not infer that the ~61s client response means this specific 30s timeout happened.
2. [Azure Functions scale and hosting, function app timeout](https://learn.microsoft.com/en-us/azure/azure-functions/functions-scale): separately documents **60s maximum to start the language worker**, not configurable. The local original `azure-functions/campaign-api/host.json` sets execution `functionTimeout=00:20:00`, so ~61s pre-handler 503 is **not** automatically caused by function-execution timeout.
3. [Azure Functions concurrency, Flex HTTP](https://learn.microsoft.com/en-us/azure/azure-functions/functions-concurrency#http-trigger-concurrency): **Python defaults to one concurrent HTTP request per instance**, even at 2048 MiB; the 2048 MiB/16 default in the table applies to *non-Python* apps. Original `infra/azure/main.bicep` and previously read-only verified Azure ARM show `runtime=python 3.12`, `instanceMemoryMB=2048`, `maximumInstanceCount=1`; a custom HTTP concurrency override was NOT returned and therefore remains **unknown** pending a current read-only ARM `functionAppConfig.scaleAndConcurrency.triggers.http.perInstanceConcurrency` query. Thus two simultaneous requests may contend for one permitted slot, but the probe also had an isolated sequential HTTP503.
4. [Official Functions errors troubleshooting](https://learn.microsoft.com/en-us/troubleshoot/azure/azure-functions/availability/functions-troubleshoot-issues) directs operators to Function App > **Diagnose and solve problems > Function App Down or Reporting Errors (Preview)**, the function configuration checks, host startup, telemetry/exception and platform ingress/instance issues. **Kudu/SCM logs do not apply to Flex Consumption**; inspect AppRequests/AppTraces/AppExceptions and FunctionAppLogs if available instead.
5. Related open Azure Functions host reports: [#11526](https://github.com/Azure/azure-functions-host/issues/11526) reports intermittent Python 3.12 Flex startup/warmup delays but has a different timescale. [#11617](https://github.com/Azure/azure-functions-host/issues/11617) documents a language-worker `StartStream` 60s startup timeout that causes a **persistent** host deadlock until restart; our intermittent success pattern is **not an exact match**. A [September 2026 Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/6000597/intermittent-60-second-http-503s-on-azure-function) describes a remarkably similar real ~60.07s unmarked HTTP503 with adjacent successes and moderator guidance to correlate worker/host logs; this is a community report, **not a confirmed Microsoft bug affecting this app**.

## Exact original DEV observations and elimination

- Protected unchanged original [#40691854364](https://github.com/saifsiddiqui59/RetailGrowthAI/actions/runs/40691854364) and approved candidate [#40755301253](https://github.com/saifsiddiqui59/RetailGrowthAI/actions/runs/40755301253) both reproduced **9/20 genuine ~61s unmarked Python Flex HTTP503** against identical anonymous synthetic `GET /api/campaigns/{fixed UUID}`, versus **0/20** on existing Free SWA Node preview. Candidate deferred HTTP/worker/Pillow/FFmpeg imports, 4/4 CI passed, core trigger registration succeeded, and the 9/20 error rate did not improve. Its fallback to prechange green source ZIP succeeded, not byte-identical proof of previous deployment.
- The 20 Python responses from candidate run: sequential initial #1 401 (1.271s), sequential initial **#2 503 (60.833s)**; four paired warm tests (#3–10) each split 1 marked 401 / 1 unmarked ~61s 503; two paired concurrent tests (#11–14) each split 1/1; after 300s idle, pair #15/16 both 401, pair **#17/18 both 503**, pair #19/20 both 401. **Single-slot concurrency might aggravate paired requests but cannot alone explain #2 or both #17/18.**
- Post-rollback original [#40759193001](https://github.com/saifsiddiqui59/RetailGrowthAI/actions/runs/40759193001) verified existing HTTP/Queue/Poster trigger registration and observed sequential **401 in 5.021s** followed by **unmarked 503 in 61.009s**. Azure AppTraces from the failed canary had `worker_start` in ten distinct UTC minute buckets 19:35–19:50, and a prior independent 6h application exception aggregate counted 158 `Microsoft.Azure.WebJobs.Script.Workers.Rpc.RpcException`. Neither the minute buckets nor broad totals prove a 503-specific worker startup failure.
- TCP/TLS completed; 503 had no **application-generated** `X-Request-ID`; both known and unknown GET routes have stalled in earlier diagnostics. This is consistent with a pre-handler path (HTTP group ingress/specialization/worker readiness), but absence of the marker does not prove that Python never ran. There is no valid basis to blame image generation, Supabase JWT checking, paid AI inference or the campaign handler itself for *these anonymous pre-dispatch responses*.
