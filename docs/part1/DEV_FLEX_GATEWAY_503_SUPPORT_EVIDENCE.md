Public Supabase JWKS GET returned 200 in 0.847 s.
2. Code-only existing DEV [#40098789883](https://github.com/saifsiddiqui59/RetailGrowthAI/actions/runs/40098789883) **successfully published** an optimized ZIP (Pillow/FFmpeg lazy imports) and verified 21/21 indexed functions and unchanged backend flags; its HTTP acceptance correctly **FAILED** because GET campaign still returned HTTP 503 in 60.954 s, while adjacent POST routes returned 401 in about 0.95 s.
3. Protected [route matrix #40100546239](https://github.com/saifsiddiqui59/RetailGrowthAI/actions/runs/40100546239), 14:01–14:03 UTC: 4 of 9 anonymous fixed-path probes timed out at 18 s, zero Python `X-Request-ID`: campaign GET, poster-job GET, poster-history GET and even an unknown GET path. Other GET and POST routes returned Function-handler 401 in 0.7–4.5 s. A final GET campaign returned 401 in 0.787 s. This is intermittent and not isolated to one API handler. Responses aborted at 18 s were **not** proven to be HTTP 503; the earlier two long probes independently confirmed actual 503 after ~61 s.
4. Existing six-hour Application Insights **aggregates** (not causally correlated): 158 `Microsoft.Azure.WebJobs.Script.Workers.Rpc.RpcException`, 12 `Microsoft.AspNetCore.Connections.ConnectionAbortedException`. Completed request durations with status 200 were generally a few seconds; some pre-handler failures were absent from application request telemetry.
5. The actual poster worker/queue did work: approved signed-in DEV poster-only [#40094276454](https://github.com/saifsiddiqui59/RetailGrowthAI/actions/runs/40094276454) PASSED 1080×1350 PNG, private signed download, correct review-selected banner and RLS cross-shop denial, via the existing authenticated tenant-scoped Supabase RPC fallback where Azure ingress failed. This is **not** successful direct-HTTP reliability or cloud 30-second MP4 proof.

## Azure Support investigation requested
Please correlate the exact UTC windows for platform HTTP ingress/response, Flex scale instance allocation and lifecycle, language-worker init/restarts/exits, Python worker gRPC channel health, instance memory/CPU, Functions host startup and authentication route dispatch. Specifically explain no Python `X-Request-ID` on failed/aborted GET and why even a nonexistent GET path could stall while nearby other requests rapidly reached the Python handler.

A separate non-configurable **60-second language-worker startup limit** exists; matching timeout is a *hypothesis*, not proof of root cause. Official documentation: https://learn.microsoft.com/en-us/azure/azure-functions/functions-scale. A contemporaneous but unverified analogous incident was reported in Microsoft's Q&A: https://learn.microsoft.com/en-us/answers/questions/6000597/intermittent-60-second-http-503s-on-azure-function.
